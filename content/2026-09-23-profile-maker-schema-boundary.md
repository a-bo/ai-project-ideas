# 不接模型，先把 AI 输出关进 Schema：Profile Maker 的一次失败演练

AI 工具最容易被忽略的风险，不是“文案不够好”，而是模型返回了一段看似正常、实际上不能发布的 JSON。

这次我把 `AI GitHub Profile Maker` 的事实层往前推进了一步：新增一个零依赖的输出校验边界。它不调用任何模型，也不假装已经有生成能力；它只负责在模型接入前，把不可信输出拦在事实层之外。

## 这次实际加入了什么

- 明确的 JSON Schema 形状：只允许 `inferences` 和 `recommendations` 两个输出字段。
- 每条推断必须有 `id`、文本、至少一个 `evidence_ids` 和 `low / medium / high` 置信度。
- 每条建议必须有 `id`、文本和至少一个 `because` 证据理由。
- 证据 ID 必须来自事实层已知集合；额外字段和未知证据一律拒绝。
- 第一次校验失败时允许调用方重试一次；第二次仍失败，返回空推断、空建议和人工填写模板，而不是半截 README。

对应实现：[输出校验模块](../examples/github-profile-fact-layer/src/output-validator.mjs)。

## 我用什么证明它有效

新增测试覆盖三种不应该悄悄放过的情况：

1. 第一次输出缺少 `evidence_ids`，第二次补齐后才通过。
2. 连续两次输出不合法，只返回确定性人工模板，且生成函数恰好被调用两次。
3. 引用了不存在的证据 ID，或夹带 Schema 外字段，均被拒绝。

这让原先的 A08 验收项从“待实现”变为自动化覆盖。运行方式仍是：

```bash
cd examples/github-profile-fact-layer
npm test
```

## 仍然没有的东西

这里没有模型 API、API Key、模型重试请求、生成 Profile README、网页、部署或效果指标。测试只能证明输出边界和降级策略符合预期；它不能证明未来接入的模型会事实准确，也不能证明生成文案能带来 Star 或关注者。

下一步应当选择一个具体模型适配器，把它的原始响应接到这个边界上，并保留本次验证失败时的可观察错误信息。
