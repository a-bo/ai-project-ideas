# 把 AI 项目方案变成代码，我先写了 10 个不会“说漂亮话”的测试

上次我为 `AI GitHub Profile Maker` 写了事实层契约。这次没有继续堆功能清单，而是把最容易出错的部分做成了一个可运行的 Node.js 示例。

它做的事情很克制：输入公开 GitHub 用户名，读取公开资料、分页获取本人仓库、预筛选最多 8 个 README，然后输出结构化 JSON。它不调用模型，也不会修改 Bio、Pinned 仓库或 README。

为什么先做这一步？因为“生成一份好看的主页”之前，必须先保证事实没有被悄悄放大。

真实运行 `a-bo` 账号时，程序识别到了一个已经存在的冲突：

- GitHub 仓库描述写着 `100+` 个项目方向；
- 仓库 README 首屏写着 `35+`。

事实层不会选更吸引人的 `100+`，而是输出 `omit_from_generated_copy`，要求先核对来源。这样后面的模型即使很会写，也拿不到把争议数字包装成事实的机会。

这次一共写了 10 个自动化测试，覆盖：

- 普通公开账号；
- 用户不存在；
- 135 个仓库的分页；
- Bio 为空；
- README 缺失；
- 描述与 README 数量冲突；
- README 中的提示注入；
- API 限流且不自动重试；
- Pinned 数据不可用时不猜测；
- 非法用户名在联网前失败。

原验收矩阵里的 A08 是“模型 JSON 缺字段”。因为当前没有模型层，我把它明确保留为 `deferred`，没有用一个假测试冒充完成。

当前证据是：Node.js 20 环境下 10/10 测试通过，并对 `a-bo` 的公开数据完成了一次真实只读运行；冲突检测、分页范围和 Pinned 不可用标记均有输出。它仍不是完整应用，没有页面、LLM、缓存、部署或 GitHub 写入能力。

代码与运行方式：[GitHub Profile Fact Layer](../examples/github-profile-fact-layer/README.md)

这一步带来的经验很朴素：AI 工具的第一版，未必应该从 Prompt 开始。先把哪些是事实、哪些是不知道、哪些存在冲突写进代码，后面的生成才有可信的地基。
