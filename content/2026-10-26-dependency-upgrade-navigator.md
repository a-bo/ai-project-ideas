# 别让 AI 直接 bump 版本：依赖升级助手该先交出哪些证据？

很多依赖升级工具把目标写成“自动更新版本号”。我更想先解决升级里最容易被忽略的一段：**为什么认为这次升级值得做、仓库哪里可能受影响、哪些验证其实还没有跑？**

今天新增的 [AI Dependency Upgrade Navigator](../ideas/ai-dependency-upgrade-navigator.md) 是一个完整项目方案。它的 MVP 不改 `package.json`，也不替你点合并；它先生成一份升级准备包：

- manifest、锁文件、CI 配置和使用点各自带路径、哈希或行号；
- 官方 release note 缺失时明确标为 `release_notes_unverified`；
- 搜索到 API 导入只代表“需要审阅”，不等于“必然不兼容”；
- `npm test` 没跑，就显示 `not_run`；
- 失败日志被导入后仍保持 `needs_human_review`，而不是替人宣布回滚或修复。

我给它列了 A01–A10 十个验收场景，最关键的一条是：每条可见结论都要回链到证据 ID；没有证据就进入未知项。这样即使后续接 LLM，它也更适合作为“提问题的助手”，而不是伪装成已经做完验证的发布机器人。

这是一份设计与实现路线，不是已运行的升级工具：没有执行依赖安装、测试、CI、代码修改或 PR 创建。下一步应先为 A01–A10 编写离线 fixture 和测试，再考虑真实仓库扫描。
