# API 升级不是一段 diff：先把“契约变化”和“待确认影响”拆开

API 升级最危险的瞬间，往往不是改代码，而是团队看到一段 diff 后默认“应该没事”。

这次我新增了 [AI API Contract Drift Reviewer](../ideas/ai-api-contract-drift-reviewer.md) 项目方案。它的第一版不拉仓库、不跑请求、不改 SDK，也不宣布接口兼容；它只处理操作者明确导入的两份契约快照和可选调用清单。

核心是把输出拆成四层：

1. **观察结果**：例如参数从 required 变成 optional、枚举值消失、字段类型变化。每条都要回链 old/new 指针和证据 ID。
2. **待人工复查项**：比如“某调用方是否仍假设这个枚举会出现？”这是问题，不是结论。
3. **覆盖未知项**：没有调用或测试清单时，必须写“未知”，不能替团队写“无影响”。
4. **人工动作**：谁需要确认服务端语义、补测试、更新迁移说明或决定忽略规则。

我尤其在意一条边界：即使以后接入模型，它也只能给已有证据写草稿；没有 pointer 和 evidence ID 的话，不能进入“已观察”层，更不能导出成兼容性结论。

这个方案已经包含输入/输出结构、MVP 模块、8 步实现路线与 A01–A10 验收条件。它目前是文档方案，**没有导入真实契约、扫描仓库、运行 API、生成代码或验证任何兼容性**。

如果把它做成第一个可运行版本，我会先只支持 OpenAPI 3.1 JSON 和合成 fixture：先验证“来源清楚、结论可回查、未知不被抹掉”，再谈连真实工程。
