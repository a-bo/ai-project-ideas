# 灰度发布不是“开 5% 看监控”

很多 feature flag 发布的风险，不在开关本身，而在交接时那句模糊的“没问题就全量”。

我刚为 [AI Project Ideas](../ideas/ai-feature-flag-rollout-reviewer.md) 新增了一个完整的 **AI Feature Flag Rollout Reviewer** 方案。第一版只接收操作者导出的开关快照、灰度计划和已脱敏的摘要观测，不接入远程 flag、监控或生产控制面。

它刻意把四类内容拆开：

1. 可回查的配置与观测事实；
2. 环境混用、阶段倒退、缺停止条件等阻断项；
3. “仍需谁确认”的问题；
4. 人工执行的放量、回滚与审批动作。

这样，`recorded_not_decided` 不会被模型写成“发布成功”，而没有回滚角色的计划也不能被包装成“可以继续”。

这次是**项目方案**，不是已经运行的发布工具：没有读取真实开关、导入生产指标、运行灰度、触发回滚或验证任何线上结果。下一步应先用合成 A01–A10 fixtures 实现离线校验，再讨论受控的本地导入。
