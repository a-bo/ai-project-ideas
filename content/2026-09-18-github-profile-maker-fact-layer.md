# 做 AI GitHub 主页工具，先解决“事实层”

我把 `AI GitHub Profile Maker` 又往可开发方向推了一步，但这次没有先写 Prompt。

原因很简单：这类工具最危险的错误，不是文案不够漂亮，而是把不一致的数据包装成确定事实。

我用公开资料做检查时就遇到一个真实例子：仓库描述写着 `100+` 个项目方向，README 写的是 `35+`。如果把两份内容一起交给模型，它很可能选更吸引人的那个数字，然后生成一句“已整理 100+ 个项目”。文案更强了，可信度却更差了。

所以这次补的 MVP 契约把输出拆成三层：

1. **事实**：直接来自 GitHub API，保留抓取时间和来源。
2. **推断**：例如“内容主要集中在 AI 应用与具身智能”，必须引用证据。
3. **建议**：例如“统一仓库描述和 README”，不能伪装成已完成成果。

遇到数字冲突时，第一版的策略不是让模型猜，而是从生成稿里省略这个数字，并在“发布前检查”中提醒用户确认。

我还加了 10 个最小验收用例：用户不存在、135 个仓库需要分页、Bio 为空、README 缺失、API 限流、Pinned 数据不可用、README 提示注入、模型 JSON 不合法等。只有这些用例有自动化测试、事实数字经过人工核对，项目才应该从“设计稿”改成“可运行 MVP”。

这次更新仍然是文档方案，没有代码、运行日志或线上 Demo。下一步不是再加功能，而是先实现 GitHub 数据抓取、归一化 Schema 和 fixture 测试，让事实层稳定下来。
