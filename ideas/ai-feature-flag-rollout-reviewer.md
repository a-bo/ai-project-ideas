# AI Feature Flag Rollout Reviewer

## 一句话

导入由操作者导出的 feature flag 配置、分批计划和观测摘要，生成一份可回查的发布 review 包：**哪些事实已经具备、哪些边界仍未知、下一步必须由谁人工确认**。

> 第一版不读取或修改任何远程开关，不连接生产指标，不自动放量、回滚或宣告发布成功。

## 目标用户

- 维护多环境 feature flag / remote config 的应用、平台与 SRE 团队
- 需要把灰度计划交接给值班、测试和产品负责人的技术负责人
- 想做可审计 AI 开发者工具作品集、但不让模型进入生产控制面的个人开发者

## 痛点

开关发布常被写成“先开 5%，看监控”，但交接时容易遗漏目标人群、版本、依赖开关、指标窗口、停止条件和回滚负责人。截图或聊天记录也很难回答：

- 这份配置究竟来自哪个环境和哪个导出时间？
- 当前百分比、受众规则和前置开关是否被完整记录？
- “无异常”是已核验的观测，还是没有人看过指标？
- 哪些风险只是一条待确认的问题，不能被 AI 写成“可以全量”？
- 发生阈值触发后，谁有权限执行什么动作？

## MVP 边界

### 输入

1. 操作者导入的开关快照：key、环境、默认值、受众规则、百分比、依赖关系与导出时间。
2. 操作者填写的灰度计划：阶段、目标版本、观察窗口、成功/停止阈值、回滚联系人。
3. 可选的**摘要化**观测记录：来源标签、时间窗、指标名、数值/状态与证据链接；不得包含用户原始日志、cookie、token 或密钥。
4. 可选人工批准记录：角色、范围、时间与审批引用。

### 输出

- 带 evidence ID 的配置与计划**观察结果**
- 必填项缺失、环境混用、阶段倒退、阈值冲突等**阻断项**
- 由固定规则生成的**待人工确认问题**
- 按阶段列出的人工动作、负责人和回滚准备清单
- 可导出的 Markdown / JSON review 包

### 不做

- 不调用 flag SDK、厂商 API、Kubernetes、CI、监控或生产数据库
- 不修改开关、不发起放量/回滚、不创建工单、不发送通知
- 不把一条摘要观测写成“系统健康”或“发布成功”
- 不由模型决定阈值、审批、生产动作或风险接受

## MVP 模块

| 模块 | 责任 | 约束 |
| --- | --- | --- |
| intake | 校验操作者导入包、环境、来源与脱敏标记 | 缺来源或重复 evidence ID 直接阻断 |
| config-map | 规范化开关、依赖和受众规则 | 保留原始导出路径与未知字段 |
| rollout-check | 校验阶段、百分比、观察窗、阈值和回滚准备 | 只报告规则命中，不输出“可全量” |
| observation-linker | 把摘要观测连到阶段与时间窗 | 无匹配一律显示为未核验 |
| review-builder | 分开事实、阻断项、待确认问题与人工动作 | 四类内容不可混写 |
| export-gate | 检查证据回链、敏感文本和结论措辞 | 不合格拒绝导出决策性结论 |

## 数据结构

~~~json
{
  "review_id": "rr_2026_11_18_checkout",
  "flags": [
    {
      "evidence_id": "E-FLAG-01",
      "key": "checkout_v2",
      "environment": "staging",
      "exported_at": "2026-11-18T09:00:00Z",
      "rollout_percent": 5,
      "depends_on": ["payment_api_v2"]
    }
  ],
  "stages": [
    {
      "stage_id": "S1",
      "target_percent": 5,
      "observation_window_minutes": 30,
      "success_rule": "human-defined KPI reference",
      "stop_rule": "human-defined error budget reference",
      "rollback_owner_role": "release-manager"
    }
  ],
  "observations": [
    {
      "observation_id": "O-01",
      "stage_id": "S1",
      "evidence_id": "E-METRIC-01",
      "source_label": "operator-export",
      "window_start": "2026-11-18T09:00:00Z",
      "window_end": "2026-11-18T09:30:00Z",
      "status": "recorded_not_decided"
    }
  ]
}
~~~

约束：一个 review 只能对应一个环境；观察记录必须指向已存在阶段；`recorded_not_decided` 不能被序列化为“通过”；任何导出文本不得含 token、cookie、Authorization 或绝对本机路径。

## 页面 / CLI 流程

1. **导入**：显示开关、环境、导出时间、脱敏状态和证据完整性。
2. **计划**：录入阶段、观察窗、停止条件、回滚负责人和审批引用。
3. **一致性检查**：展示环境混用、依赖缺失、百分比倒退和阈值缺口。
4. **观测关联**：按阶段显示已记录、未关联和时间窗不匹配的摘要。
5. **Review 包**：分别输出事实、阻断项、待确认问题和人工动作。
6. **导出门禁**：在证据、敏感文本、角色或免责声明缺失时拒绝导出。

## 推荐技术栈

- Node.js 20+、TypeScript、JSON Schema
- 纯函数规则引擎与固定 JSON fixtures
- 可选本地 CLI；第一版无需数据库、LLM API 或远程 flag 权限
- 后续如有模型，只能为已有 evidence 生成措辞草稿，并经过 Schema 与人工 review

## 实现步骤

1. 定义单环境输入 Schema、evidence ID 格式和敏感文本拒绝规则。
2. 先实现导入校验：缺环境、重复证据、绝对路径和未脱敏字段必须失败。
3. 实现阶段检查：百分比范围/顺序、观察窗、停止条件与回滚角色。
4. 实现依赖和观测关联，输出“已记录”“未核验”“无法关联”三种事实状态。
5. 用固定规则生成问题，不生成放量或回滚建议。
6. 输出分层 review JSON 和 Markdown；禁止将待确认项渲染成通过结论。
7. 编写 A01–A10 合成 fixtures 和零依赖测试。
8. 通过合成测试后，再考虑**只读、本地、显式选取文件**的导入器。

## 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 单环境合法输入 | 每个事实均有 evidence ID 和来源时间 |
| A02 | 混入第二环境 | intake 阻断，不能生成 review |
| A03 | 5% 后计划回到 1% | 标出阶段倒退，要求人工说明 |
| A04 | 缺停止条件 | 标为阻断项，不输出“可继续” |
| A05 | 观测无对应阶段 | 保留为未关联事实，不能当作验证 |
| A06 | 观测时间窗不匹配 | 标为未核验，不推断指标健康 |
| A07 | 依赖开关缺失 | 标出依赖未知与人工动作 |
| A08 | 含 token/cookie 文本 | export-gate 拒绝输出 |
| A09 | 仅有 recorded_not_decided | 禁止写成“发布成功” |
| A10 | 无回滚角色或审批引用 | 输出人工确认问题，不创建任何远程动作 |

## 已实现的离线示例

- [零依赖结构校验器](../docs/feature-flag-rollout-reviewer-validator.md)已覆盖 A01–A10 的合成输入：单环境、证据 ID、阶段顺序、停止条件、回滚角色、观测归属、敏感文本与禁止成功结论。
- [示例目录](../examples/feature-flag-rollout-reviewer/README.md)可在 Node.js 20+ 运行；它只验证合成或脱敏记录的结构，不连接远程 flag 或生产系统。

## 可扩展方向

- 对接操作者下载的不同厂商导出文件，但保持离线解析
- 增加人工签名、变更单链接与留存 hash
- 为已验证的 review 包生成发布说明草稿
- 引入只读指标快照前先定义数据保留、脱敏和权限模型
- 将多开关依赖图可视化，但不赋予工具执行权限

## 简历 / 作品集包装

> 设计并实现 feature flag 灰度发布的证据化 review 工具：将操作者导入的配置、阶段、摘要观测和人工职责分层，阻断环境混用与无证据的成功结论。

展示时使用完全合成的单环境数据，演示“导入 → 找到阶段缺口 → 关联观测 → 导出待人工确认的 review 包”。不要把合成校验描述为真实生产发布验证。

## 开源传播标题

- 灰度发布不是“开 5% 看监控”：先把证据、阈值和回滚责任写清楚
- 不让 AI 替你点全量：一个 Feature Flag Rollout Reviewer 的 MVP
- 发布前的 review 包，应该把“已观察”和“待决定”分开
